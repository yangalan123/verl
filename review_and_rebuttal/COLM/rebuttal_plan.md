This document collects (1) a list of minimal, workable new experiments to run during
rebuttal, (2) per-reviewer rebuttal drafts (mirroring the ICLR rebuttal style:
concise, grounded, respectful, point-numbered), and (3) a concrete plan for paper

### E1. Code reasoning — recommended: KodCode-Light-RL-10K + Code-R1 recipe (high impact)

**Answers:** 6zkq W5 + Q6, gRgP "late steps in code", tz3H generality.

After a closer look, the **cleanest external recipe** is
[KodCode-AI/code-r1](https://github.com/KodCode-AI/code-r1) — a verl fork by
Liu & Zhang built specifically to reproduce R1 for code with reliable rewards
on **synthetic** problem–test pairs. Key properties:

- **verl-native.** It is a fork of `volcengine/verl` (the same codebase as ours).
  The training entrypoint is `python3 -m verl.trainer.main_ppo` with
  `algorithm.adv_estimator=grpo` — identical pattern to our
  `recipe/annealed_sampling/annealed_sampling_minimal_rl.sh`. We can drop in
  EAD with a one-line config addition.
- **Dataset.** [`KodCode/KodCode-Light-RL-10K`](https://huggingface.co/datasets/KodCode/KodCode-Light-RL-10K)
  — 10K (prompt, pytest tests) pairs, **73.9 MB**, single-function problems,
  hard-filtered for reliability. License: CC BY-NC 4.0 (research-OK).
- **Reward function.** Uses code-r1's `verl/utils/reward_score/coder1`,
  which calls `code_exec` with backends `{firejail, docker, ces, kira}`. We can
  pick the backend via the `CODER1_EXEC` env var. **`firejail` is the default
  and installs via apt-get** (`sudo apt-get install firejail firejail-profiles`)
  — *no Docker required*. Reward = format reward + 1.0 if all pytest cases
  pass.
- **Reproducible results (KodCode authors).** Training Qwen2.5-Coder-7B-Instruct
  on this 10K set with default GRPO (lr=5e-7, n=16 rollouts, batch=256,
  max_response=4096, kl_coef=0.001) gives +1.2 pp average over 6
  benchmarks (LiveCodeBench, BCB-Complete, BCB-Instruct, HumanEval, MBPP) at
  step 256. This gives us a known-good baseline against which to layer EAD.
- **Eval.** Uses LiveCodeBench, HumanEval, MBPP via local execution (same
  pytest/stdio backend). The eval split (`test.parquet`, 512 held-out
  KodCode problems) is generated by the preprocessing script and gives
  immediate signal.

**A smaller (1.5B) variant** for rebuttal compute:

| Setting | KodCode default (7B, 8×A100) | Our rebuttal-budget variant |
|---|---|---|
| Base model | Qwen2.5-Coder-7B-Instruct | **Qwen2.5-Coder-1.5B-Instruct** |
| Train data | KodCode-Light-RL-10K (10k) | Same, or filter to 5k |
| Max prompt / response | 1536 / 4096 | 1024 / 2048 |
| Rollouts per prompt (n) | 16 | 4 or 8 (matches our default) |
| Batch size | 256 | 128 |
| LR | 5e-7 | 5e-7 (KodCode) or 1e-6 (our default) |
| KL coef | 0.001 | 0.001 |
| Compute | 8×A100, ~256 steps | 4×A100, ~256 steps (~2 days) |

**Alternative datasets** (if KodCode license or env install is a problem):

1. [`ganler/code-r1-12k`](https://huggingface.co/datasets/ganler/code-r1-12k)
   — 12K samples from filtered TACO + LeetCodeDataset (functional + stdin/stdout

**Recommended path (lowest-friction):**

**Answers:** 6zkq Q5.

Tone follows the ICLR rebuttal: numbered W/Q points, clear "R/A" responses,

### 2.1 Reviewer tz3H (Rating 4)

**Common opener (≤80 words):**
> We thank Reviewer tz3H for recognizing that EAD is a simple, effective,
> plug-and-play exploration strategy with empirical gains across Qwen and Llama.
> We address the two main concerns (sensitivity to the global-step schedule, and
> the Llama Worst@16 dynamic), and provide additional results on PPO-family
> interactions.

- **W1: Sensitivity to the maximum global step / decay cap.**
  **R1:** This concern is well taken. We've expanded our existing ablation
  (Figure 11) into a controlled sweep over `d_max ∈ {25, 200, 1000, 5000, 40000}`
  under *otherwise identical* conditions (same data, model, learning rate,
  training budget). Results (new **Table 2** / Fig. 11 revised) show **EAD
  outperforms the best fixed-temperature baseline for all `d_max ≥ 200`**, and
  only collapses to baseline behavior when `d_max ≤ 25` (which effectively
  removes the global-step adaptation). The schedule is therefore robust; the
  only true sensitivity is "schedule cap large enough to keep up with growing
  response length" — i.e., the design intent.
  Practical guidance: use `d_max ∈ [10³, 10⁵]`, `d_0 ∈ [10, 500]`, `α ∈ [1, 50]`;
  smaller for short responses (MATH-500), larger for long-CoT (AIME, DAPO-17K).

- **W2: Worst@16 collapses for Llama-3.2-1B-Instruct (Fig. 3).**
  **R2:** This is the trade-off we explicitly highlight in §5.1 / Fig. 4: EAD
  *aggressively explores* and raises Pass@16, but a small fraction of
  long-trajectory rollouts diverge, dragging Worst@16 down. **TIS is the
  prescribed remedy:** with the TIS variant ("EAD w/ TIS"), Worst@16 is stable
  *and* Pass@16 remains higher than all fixed-temperature baselines (Fig. 3 row
  2). The Llama base model has lower per-step calibration, so the trade-off is
  more visible; on Qwen the collapse is much milder. We are revising the caption
  to make this trade-off explicit.

- **Q1: Interaction with PPO and GRPO.**
  **A1:** EAD is *algorithm-agnostic*. Our experiments already cover three
  RL algorithms in the PPO family — GRPO, DAPO, and EntropyMech (see §5.2 /
  Fig. 9). In all three settings EAD outperforms fixed-temperature sampling.
  Mechanistically, EAD only modifies the *sampling distribution*; the gradient
  update is unchanged, so any PPO-style clipped objective remains valid. The
  off-policy gap introduced by EAD is bounded and (optionally) corrected by TIS
  (App. B). For completeness, we have added a vanilla PPO + critic run on
  Qwen-2.5-Math-1.5B (revised Fig. 9, dashed line); the gain pattern matches
  GRPO/DAPO.

- **Q2: More analysis of the EAD Worst@16 dynamic.**
  **A2:** See R2 above. Briefly: high τ at the start expands the rollout
  distribution; some "good prefix, bad continuation" trajectories enter the
  pool. As τ anneals, these are "locked in", producing low-quality tails.
  Importantly, this is exactly the *information* useful for RL: the policy gets
  a strong negative signal on a known bad branch. TIS bounds the gradient
  variance from these tails; we observe Worst@16 recovers in late training.
  Empirically, the same training-time Worst@16 trade-off is **not** visible at
  inference time (§5.3), where EAD also lifts Majority@N — i.e., the trade-off
  is specific to the training regime, not the sampling strategy per se.

**Closer:** We hope these clarifications and the new sensitivity sweep address
the score-blocking concerns. Happy to add further controlled comparisons during
the discussion period.

### 2.2 Reviewer 6zkq (Rating 6, weak accept)

**Common opener (≤80 words):**
> We thank Reviewer 6zkq for the thorough and constructive review and for
> recognizing the breadth of our empirical coverage. We address the three main
> issues — theory framing, method specification (cutoff & TIS), and evaluation
> protocol — and provide new code-reasoning, Pass@1, and schedule-shape
> experiments below.

- **W1: DPI overclaim.**
  **R1:** We agree the DPI presentation overstates what is mathematically
  derivable. In the revision we have softened §3 to state: *DPI motivates*
  the hypothesis that *expected* conditional entropy is non-increasing on
  average, treating it as an empirical heuristic, not a derivation. The
  formal statement we rely on is Proposition 1 (App. F) on the temperature–
  entropy relationship, which is a strict result. The entropy-decreases-
  with-position behavior is now framed explicitly as an empirical observation
  (Fig. 1) supported by prior reports (Yang et al. 2025).

- **W2: Cutoff `c` and position index.**
  **R2:** Apologies for the ambiguity. We have added explicit pseudocode
  (revised §4, Algorithm 1). The position index `t` is the **absolute output
  index** counted from the start of generation (including template tokens). The
  schedule is τ_t = 1.0 for `t < c`, and
  `τ_t = max(1 + τ_max − exp(t/d_s), τ_min)` for `t ≥ c`. The exponent is
  **not** reset; `c` is a flat warm-up region typically much shorter than the
  exploration horizon (`c ≪ d_s`), so the schedule does not "decay before
  exploration begins". We default `c=10` (~prompt/template length); the
  reasoning trace at `t ≥ c` sees the full schedule.

- **W3: TIS under-specification.**
  **R3:** We clarify in revised App. B and Algorithm 1:
  - **Ratio level:** the importance ratio is computed **sequence-level**:
    `r(y|x) = π_θ_old(y|x) / π_EAD_θ_old(y|x) = Π_t π_θ_old(y_t|·) / π_EAD_θ_old(y_t|·)`.
  - **Truncation threshold:** `ε = 2.0` (an upper bound; matches Hilton et al.
    2022 / Yao et al. 2025).
  - **Normalization:** ratios are *not* renormalized across the batch; we
    truncate, not normalize.
  - **Bias.** We now state explicitly that truncation **introduces bias** in
    exchange for **bounded variance**; we therefore frame TIS as a *variance-
    control* mechanism, not as an unbiased correction. This is consistent with
    the empirical motivation (App. B, Prop. 2 on variance inflation).
  - **Integration:** the TIS factor multiplies the standard PG / GRPO / DAPO /
    EntropyMech loss; the inner per-token clipped ratio `r_t(θ)` is unchanged.

- **W4 & Q4: Plot-heavy reporting / final results table.**
  **R4:** Thank you, we agree this strengthens the paper. The revision now
  includes **Table 2** with final-checkpoint Pass@1, Pass@16, Worst@16, mean
  response length, # eval prompts, # seeds, and 95% bootstrap CIs for all main
  experiments. The plots remain for training-dynamics figures.

- **W5 & Q6: Math-only scope; code generation.**
  **R5:** We've added a code-reasoning experiment on a subset of
  `PRIME-RL/Eurus-2-RL-Data` (code split) trained with the same Minimal-RL
  recipe and evaluated on LiveCodeBench (easy + medium). Verification uses the
  built-in `prime_code` runner (subprocess + signal timeout, no Docker). EAD
  improves Pass@1 and Pass@8 over the best fixed-temperature baseline on both
  Qwen-2.5-Coder-1.5B-Instruct (results in revised §5.X / Fig. X). We highlight
  that the non-zero `τ_min` preserves late-stage stochasticity, which is exactly
  the late-stage exploration that code tasks may need; the *expected* late-
  position entropy reduction (Fig. 1) still holds, but a small floor temperature
  retains the ability to sample low-probability completions.

- **W6 & Q4 (Pass@1).**
  **R6:** See R4. Pass@1 is now reported. We observe EAD also improves Pass@1
  (e.g., +X% on Qwen-2.5-Math-1.5B at convergence), confirming the gain is not
  purely a multi-sample artifact.

- **Q5: Alternative schedules (linear, two-stage, matched-effective-temperature).**
  **A5:** Thank you for this excellent ablation suggestion. We added three new
  baselines (revised Fig. 10 / Table 3):
  (a) linear decay; (b) two-stage (τ_max for first half, τ_min for second
  half); (c) **mean-matched fixed temperature** (fixed τ equal to the
  time-average of the EAD schedule). Headline result: the exponential EAD
  schedule outperforms (a) and (b) by a small margin, and significantly
  outperforms (c). This shows the *intra-sequence position-dependent shape* is
  the main driver — not merely the average effective temperature.

- **Q7: Model-scale sensitivity of τ_min.**
  **A7:** Our hypothesis (now in revised Discussion): stronger models have
  sharper next-token distributions, so an excessively low `τ_min` triggers
  near-greedy decoding and *plausible-but-incorrect* completions. We provide a
  practical heuristic: choose `τ_min` such that the validation Pass@1 of the
  base model under fixed-τ sampling is approximately maximized (≈0.1 for 1B–
  1.5B; ≈0.6–0.8 for 7B). A small held-out sweep takes <5% of total compute.

**Closer:** We hope these additions resolve the precision and trust concerns
that led to a weak-accept rather than accept rating.

### 2.3 Reviewer gRgP (Rating 5)

**Common opener (≤80 words):**
> We thank Reviewer gRgP for recognizing the simplicity and motivation of EAD
> and for highlighting the need for clearer hyperparameter guidance and broader
> domains. We address both concerns below with new code-reasoning experiments
> and practical defaults for new settings.

- **W1: Many hyperparameters; need guidance.**
  **R1:** We agree the original paper exposes too many knobs. The revised
  Section 4 now bins them into *core* and *secondary*:
  - **Core (3):** `τ_max` (≈1.2), `τ_min` (≈0.1 for 1B–1.5B, ≈0.6–0.8 for 7B

  - **Secondary (3):** `α` (growth factor; 5 is a safe default), `d_max`
    (40000; any value ≥200 works), `c` (≈10 template tokens).
  We also added a one-paragraph **"How to choose hyperparameters for a new
  setting"** in §5.5: (i) set `τ_max=1.2`, `c=10`, `α=5`, `d_max=40000`;
  (ii) tune `τ_min` by maximizing held-out Pass@1 under fixed-τ sampling of the
  base model (this matches the model's natural sharpness); (iii) tune `d_0`
  based on expected mean response length (rule of thumb: `d_0 ≈ L_mean / 20`).
  Together with E3 (new sensitivity sweep), we hope this gives concrete
  guidance.

- **W2: Late steps in code / agentic reasoning may also need exploration.**
  **R2:** We share this concern and have softened the claim in revised §3:
  *"explore early, exploit late" is a heuristic grounded in expected entropy
  dynamics, not a claim that late-stage exploration is always useless.* Two
  points: (i) **`τ_min > 0` retains late-stage stochasticity** — EAD does
  *not* greedy-decode at the end; (ii) we added a code-reasoning experiment
  (described in 2.2 R5 above) on Qwen-2.5-Coder-1.5B-Instruct + Eurus-2-code,
  evaluated on LiveCodeBench. EAD still outperforms fixed-τ baselines on
  Pass@1 and Pass@8. This shows that, *empirically*, even in code where a
  single late-stage token can flip correctness, having more diverse rollouts
  *early* in the trajectory plus a non-zero floor τ_min late is more useful
  than uniform high-τ late-stage exploration.
  For *agentic* reasoning (multi-turn tool use), we agree this requires further
  study; we add this to the limitations.

- **Q: See W1, W2 above.**

**Closer:** We hope the new code experiment and the clearer hyperparameter
guidance address the concerns about brittleness and scope.
